# AI 물품 소유 확인 개발 기록

분실물 찾기 페이지에서 시작되는 소유 확인 과정 전체의 백엔드 개발 공간이다. 페이지의 요청을 받아 물품 조회·검색·매칭·질문 생성·답변 처리·평가를 수행하고 최종 소유 확인 결과를 선재의 백엔드에 전달하는 기능을 담당한다. 설계, Gemini 연동 실험, 구현 과정과 결정 근거를 이 폴더에서 관리한다.

이 문서는 초기 개발 기록이다. 확정 사항과 검토 후보를 구분하며, 예시나 실험 결과만으로 최종 규격이 확정된 것으로 간주하지 않는다.

작성 기준일: 2026-11-10 · 기존 질문 생성의 실제 API 실험일: 2026-10-14

2026-11-10 자유 설명 검색부터 객관식 문답과 결과 인계까지 [개발용 백엔드 흐름](workflow.md)을 구현했다. 운영 판정 기준, 공통 인증·실데이터 연동 및 선재 백엔드에서의 소비 방식은 협의 대상이다. 사진 선택은 별도 후속 범위로 둔다.

2026-11-02 담당자가 범위를 명확히 했다. 분실물 찾기 페이지에서 동작하는 서버 처리 전체를 담당하며, 이 흐름의 API·입력 검증·DB 조회·후보 검색 및 매칭·검증 세션과 상태 관리·질문 생성·답변 수신 및 평가를 포함한다. 최종 소유 확인 결과의 인계 대상은 선재의 백엔드다. 화면과 중간 요청·응답의 연결, 기존 DB·공통 백엔드 규격은 관련 담당자와 조율한다. 최종 결과의 상태값·판정 기준·전달 방식은 아직 확정하지 않았다.

질문 생성 호출 코드·입출력 검증·자동 테스트·실험 실행 도구를 로컬에 준비했다. 2026-10-14 Gemini 실제 요청 7회를 수행하여 원본 응답과 [실험 결과 검토](experiments/results/question_generation_live_review_20261014.md)를 기록했다. API 연동은 확인했지만 부분 힌트 노출과 반복 결과 차이가 발견되어 질문 품질 개선이 필요하다. 실행 방법은 [실험 안내](experiments/README.md)에 정리한다.

## 1. 기능의 목적과 범위

사용자가 분실물 찾기 페이지에서 요청을 보낸 시점부터 관련 백엔드 처리를 수행한다. 보관된 물품 정보와 검색 입력을 비교해 후보를 찾고, 필요한 질문·답변을 수집·평가하여 소유 확인 결과를 선재의 백엔드에 전달한다.

개발의 출발점은 **물품 정보가 이미 DB에 등록되어 있다는 가정**이다. 최초 논의에서 물품 종류와 색상을 예시로 언급했지만, 소유 확인에 필요한 필수 피처 목록은 정하지 않았다.

이 파트에서 검토하고 개발할 내용은 다음과 같다.

- 프런트엔드가 호출하는 분실물 찾기·소유 확인 API와 입력 검증
- 기존 DB의 물품·특징 조회와 필요한 검증 기록의 저장·조회
- 사용자 검색 입력 해석과 등록된 물품 특징의 비교
- 후보 물품 검색·매칭과 결과 형식
- 검증 세션·선택된 물품·질문·답변의 연결과 진행 상태 관리
- 소유 확인에 필요한 물품 정보와 사용자 제출 정보
- Gemini에 전달할 입력과 프롬프트
- Gemini 응답의 구조화와 해석 방법
- 소유 확인 절차의 후보 방식과 비교 실험
- 평가 결과를 종합한 최종 소유 확인 결과와 선재의 백엔드에 전달할 성공·실패 계약

물품 촬영·등록·이미지 특징 추출은 이 파트에 정보를 제공하는 별도 업무다. 계정 로그인이나 실명 본인인증도 물품 소유 확인과 구분하여 팀과 협의한다. 촬영 장치 제어, 보관함 개방, 회수 코드 발급의 구현 위치와 연결 방식은 관련 담당자와 정한다.

## 4. 설계 검토

### 4.1 처리 흐름의 검토 출발점

11/10 구현한 개발용 흐름은 아래와 같다. 구현과 검증 방법은 [워크플로 계약](workflow.md)을 따른다.

```text
자유 설명 입력 → Gemini로 명시된 단서 추출 → Gemini로 DB 보관 물품 특징과 비교
    → 후보 없음 또는 추가 단서 안내
    → 후보가 있으면 확인 시도 생성·5지선다 질문 하나 제공
    → 사용자 선택을 서버에서 비교·후보와 확인 근거 갱신
    → 다음 질문 또는 개발용 판정 결과 생성
    → 선재의 백엔드가 내부 함수로 결과 조회
```

### 4.2 비교할 수 있는 후보 방식

| 후보 | 검토 내용 |
| --- | --- |
| 사용자 설명과 등록 정보 비교 | 사용자 설명만으로 구별할 근거가 충분한지 |
| 추가 질문·답변 | 부족한 정보를 보완할 수 있는지와 질문의 적절성 |
| 사진 비교 | 사용자가 사진을 제공할 수 있는지와 비교에 도움이 되는지 |
| 복수 방식 조합 | 확인 품질 개선 효과가 추가 시간·비용·사용자 부담에 비해 적절한지 |

검토 과정에서는 실제 소유자를 확인할 수 있는지, 비소유자를 잘못 인정하는 경우가 있는지, 정보가 부족할 때 판단을 보류할 수 있는지 살펴본다.

### 4.3 정보와 결과 형식의 검토 항목

| 구분 | 확인할 내용 |
| --- | --- |
| 물품 정보 | 실제 DB 필드, 사진 존재 여부, 각 값의 생성 방식과 신뢰도 |
| 사용자 정보 | 제출 가능한 설명·사진, 기억하지 못한 항목의 표현 방법 |
| Gemini 입력 | 사용할 필드, 누락 정보 표현, 프롬프트 구성 |
| Gemini 출력 | 비교 근거, 일치·불일치·확인 불가 등을 표현하는 형식 |
| 백엔드 전달 결과 | 관련 물품·요청 식별 방법, 분석 결과와 오류의 구분 |

위 항목은 검토 목록이다. 필드명, 데이터 타입, 필수 여부, 상태값은 팀 협의와 실험 후 정한다.

## 5. 다른 파트와 협의할 내용

- 오정민의 이미지 분석 파트: 추출 필드·타입·필수 여부, 카테고리, 두 사진의 특징 통합, 확인 불가 값·출처, 검색·질문에 필요한 정보와 공개 범위
- 프런트엔드 파트: 검색 입력 항목, 후보 표시·선택, 추가 질문 화면, 결과 안내 방식
- 선재의 백엔드·DB 담당: 공통 데이터 구조·기존 조회 기능 재사용·라우터 연결·저장 구조·인증 연계와 최종 소유 확인 결과 수신·후속 사용 규격. 이 파트의 API·조회·상태·평가 구현 책임을 다른 담당에게 넘기는 의미는 아님
- 보관함 연동 파트: 소유 확인 이후 반환 절차의 시작 조건과 회수 완료 기록

선행 협의는 정민의 분석 출력 → 선재의 등록 DB 저장 → 이 파트의 조회·검색·질문·평가 입력을 맞추는 것이다. 현재 `schemas.py`와 합성 사례는 질문 생성 실험용 계약이며 정민이 그 형식으로 실제 결과를 제공한다고 확정한 것이 아니다. `visibility`·`verified`·`distinguishing`을 누가 어떤 근거로 정할지도 함께 합의한다. 상세 항목은 [설계 문서의 선행 협의](design.md#21-특징-데이터의-선행-협의)를 따른다.

이 폴더에는 담당 기능의 상세 설계와 실험 기록을 남긴다. 팀과 합의한 API, 입출력 규격, 파트 간 협업 사항은 루트 `docs/`에 정리하고 여기에서 해당 문서를 연결한다.

## 6. 실험 계획과 기록

합성 입력으로 실제 API 실험을 수행했다. [실험 안내](experiments/README.md)에서 계획·실행 방법·기록을 함께 확인할 수 있다. 원본 JSON의 자동 수집값은 보존하고 응답에서 발견한 문제와 검토 의견은 별도 Markdown에 기록했다. 기대 상태 일치와 자동 테스트 통과를 소유 확인 정확도로 해석하지 않는다.

### 6.1 검토할 사례

- 실제 소유자가 구별 가능한 특징을 정확히 설명한 경우
- 실제 소유자가 일부 특징을 기억하지 못하거나 다르게 표현한 경우
- 비슷한 다른 물품의 특징을 제출한 경우
- 종류·색상처럼 흔한 특징만 일치하는 경우
- DB 정보에 구별할 근거가 부족하거나 서로 충돌하는 경우
- 같은 입력을 반복했을 때 결과가 달라지는 경우
- API 요청 실패 또는 정해진 형식으로 해석할 수 없는 응답이 발생한 경우

사례에는 예상 결과와 그 근거를 먼저 작성한다. AI 응답이 기대와 일치했다는 사실만으로 소유 확인 방식의 적합성을 확정하지 않는다.

### 6.2 실험 기록 양식

아래 양식을 실험별로 복사하여 작성한다.

```text
실험 ID / 실행 날짜:
확인하려는 질문:
사용 모델 / 생성 설정:
실험 코드 / 프롬프트 버전:
입력 데이터 / 사례의 예상 결과와 근거:
반복 횟수:
원본 응답 / 정리한 결과:
처리 시간 / 비용 또는 사용량(확인 가능한 경우):
관찰한 문제:
해석과 한계:
다음에 변경하거나 확인할 내용:
결과 파일 위치:
```

평가 항목은 실제 소유자 확인 여부, 비소유자의 잘못된 인정 여부, 정보 부족 처리, 반복 결과의 일관성, 처리 시간과 비용 등을 검토한다. 목표 수치와 통과 기준은 아직 정하지 않았다.

## 9. 폴더 운영

파일의 역할은 다음과 같다.

- `design.md`: 상세 설계와 백엔드 협의안
- `workflow.md`: 개발용 자연어 검색·객관식·결과 인계의 실행 계약
- `api.py`, `search.py`, `workflow.py`, `workflow_ai.py`, `workflow_schemas.py`: 개발용 API, 후보 검색, 문답·판정, Gemini 연동 및 입출력 형식
- `experiments/README.md`: 실험 목적·실행 방법·검증 결과
- `experiments/data/question_cases.json`: 합성 입력 6개와 기대 상태
- `experiments/prompts/question_generation.txt`: 질문 생성 프롬프트 초안
- `schemas.py`, `gemini.py`: 실험 입출력 검증과 Gemini 질문 생성
- `tests/test_gemini.py`: 가짜 응답 기반 자동 테스트
- `experiments/generate_questions.py`: 호출 없는 계획 검증 및 실제 실험 실행
- `experiments/ownership_live_corpus.py`, `experiments/run_ownership_live.py`: 합성 DB 생성 및 실제 Gemini 워크플로 검증
- `experiments/results/`: 원본 실행 JSON·자동 요약·별도 검토 기록

기존 질문 생성과 10/13·10/14 실험 기록은 보존한다. 새 워크플로의 테스트는 별도이며, 이전 실험 결과를 객관식 흐름의 검증으로 해석하지 않는다. 실제 API 키는 백엔드 설정과 환경변수를 통해 관리한다.

Git 작업은 사용자 GitHub 계정으로 진행한다. 별도 브랜치 요청이 없으면 `main`에서 작업하며, **푸시는 사용자가 명시적으로 요청했을 때만 수행한다.**
