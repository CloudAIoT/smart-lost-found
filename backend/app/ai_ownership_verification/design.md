# 소유 확인 설계 및 백엔드 연동 초안

작성일: 2026-10-13 · 수정일: 2026-11-10 · 상태: 개발용 소유 확인 흐름 구현, 운영 계약 미합의

## 1. 목표와 이번 범위

물품 특징을 받아 소유자가 설명할 수 있는 질문을 만들고, 이후 사용자 답변을 평가하는 흐름을 검토한다. 2026-10-13 담당자가 이 흐름을 첫 실험 방향으로 선택했다.

2026-11-02 담당자가 분실물 찾기 페이지에서 시작되는 서버 처리 전체와 최종 소유 확인 결과 생성까지 담당한다고 명확히 했다. API 요청 수신·입력 검증, DB 물품 조회, 검색·후보 매칭, 검증 세션·진행 상태 관리, 질문 생성·제공, 답변 수신·저장·평가를 포함한다. 최종 소유 확인 결과의 인계 대상은 선재의 백엔드다. 화면 입출력과 운영 결과 처리 방식은 관련 담당자와 조율한다.

11/10 [개발용 소유 확인 워크플로](workflow.md)를 구현했다. 아래 자유 질문 스키마와 10/14 실제 API 결과는 이전 질문 생성 실험에 해당한다. 새 흐름은 별도 객관식 계약과 개발용 판정 기준을 쓰며 팀의 운영 상태값·점수·임계값을 확정하지 않는다. 반환 코드 발급·보관함 개방 조건은 관련 담당자와 협의한다.

## 2. 팀 구현과 연결

최초 설계 확인 기준은 main의 `4a07dbd`이며, 2026-10-20 main `5f9c4da` 기준으로 특징 저장 구조와 분석 연결부를 재확인했다.

- 백엔드는 등록·순차 촬영·분석 연결부·보관·내부 검색을 구현했다. [구현 현황](../../docs/implementation-status.md)을 따른다.
- 이미지 분석 결과는 현재 등록의 `analysis_features` JSONB에 저장된다. 실제 특징 스키마는 아직 합의 전이다.
- [이미지 분석 파트](../../../imageprocess/README.md)는 특징 추출을 담당한다. 소유 확인 Gemini 선택이 이미지 분석 모델을 결정하지 않는다.
- 현재 질문 생성 하위 모듈은 DB를 직접 조회하지 않고 전달된 특징을 받는다. 이를 호출하는 소유 확인 서비스에서 물품 조회·입력 변환·진행 상태 관리를 구현한다.
- 개발용 FastAPI 라우터와 등록 물품 조회·확인 시도 저장을 연결했다. 기존 등록 분석기의 실제 연결이나 운영용 공개 API를 구성하지 않았다.

### 2.1 특징 데이터의 선행 협의

2026-11-02 GitHub main과 `imageprocess_edit`를 확인했다. 이미지 분석 파트는 10/11 작성한 README 설계 초안이 있고 추출 결과·입출력·성공 기준은 확정 전이다. 종류·색상·재질·브랜드·문구·구별되는 특징·요약은 후보 목록이다. 백엔드에는 카테고리 테이블과 `analysis_features` JSONB 저장 틀이 있지만, 최종 카테고리 목록과 분석 JSON 내부 필드의 팀 계약은 아직 없다. PR #15의 특징 메타데이터·질문·답변 저장 구조도 제안이다.

팀 `main`의 이미지 분석 시제품은 위 7개 필드를 출력한다. 이번 개발용 검색은 그중 요약 `description`을 제외한 6개 특징과 별도의 습득 위치를 비교한다. 비공개·확인·구별 가능 여부는 별도의 검토 정보로 관리한다. [PR #17](https://github.com/CloudAIoT/smart-lost-found/pull/17)

정민·선재와 다음 항목을 합의해야 실제 데이터 연동을 구현할 수 있다.

| 항목 | 정할 내용 |
| --- | --- |
| 카테고리 | 품목 목록·코드·표시명, 사용자 선택과 이미지 판단이 다를 때 처리 |
| 분석 출력 | 실제 추출 가능한 필드·타입·필수 여부와 정상 JSON 예시 |
| 누락·불확실 정보 | null·누락·확인 불가의 구분과 관찰 출처. 불확실한 값을 확인된 정답으로 취급하지 않음 |
| 사진 두 장 | 각 사진에서 추출한 결과의 통합·충돌 처리, 사진 ID·물품 ID 연결 |
| 공개·질문용 특징 | 공개 여부·확인 여부·구별 가능 표시의 결정 주체와 근거 |
| 등록 DB 저장·조회 | 정민 출력과 선재의 등록 저장 형식, 이 파트가 읽을 형식·특징 ID·형식 버전 |
| 연동 예시 | 정상·특징 누락·판독 불확실 사례를 같은 형식으로 전달·저장·조회할 수 있는지 |

현재 질문 생성의 `schemas.py`와 합성 입력은 이 협의를 위한 실험안이다. 정민의 실제 출력이나 최종 DB 계약으로 간주하지 않는다. 형식이 정해지면 이 파트에서 필요한 조회·변환·검색·소유 확인 로직을 연결한다.

근거: [이미지 분석 초안](https://github.com/CloudAIoT/smart-lost-found/blob/main/imageprocess/README.md), [현재 API 계약](https://github.com/CloudAIoT/smart-lost-found/blob/main/docs/api.md), [ERD·기능 명세 제안 PR #15](https://github.com/CloudAIoT/smart-lost-found/pull/15).

## 3. 처리 흐름

### 3.1 전체 담당 흐름

~~~text
프런트엔드의 분실물 찾기 API 요청
  → 자유 설명 검증·Gemini 단서 추출
  → DB 보관 물품 조회·Gemini로 유사 후보 검색
  → 검증 세션 생성·다음 5지선다 질문 하나 제공
  → 선택을 서버에서 비교·답변 저장·후보와 근거 갱신
  → 다음 질문 또는 개발용 판정
  → 선재의 백엔드가 읽을 내부 결과 제공
~~~

Gemini의 후보 검색 결과로 확인할 물품을 정하고, 서버가 문답으로 확인된 비공개 특징을 바탕으로 판정한다. 개발용 결과는 `get_ownership_result` 내부 함수에서 조회할 수 있다. 선재의 백엔드가 운영에서 이 결과를 처리하는 방식은 협의가 필요하다. [개발용 계약](workflow.md)

### 3.2 기존 자유 질문 생성 실험

~~~text
백엔드의 대상 물품 특징
  → 실험 입력 형식으로 검증
  → 비공개·확인됨·구별 가능 조건에 맞는 특징 선별
  → 근거 없음: 정보 부족 반환
  → 근거 있음: Gemini에 질문 생성 요청
  → 완료 응답·JSON 구조·특징 참조·정답 문자열 노출 검사
  → 내부 검토용 질문 묶음 반환
  → 후속: 질문을 사용자에게 표시하고 답변 수집
  → 후속: 소유 확인 서비스의 답변 평가·최종 결과 반환
~~~

비공개 여부와 검증 가능성을 구분하는 것은 이번 실험의 선택이다. 최종 공개 범위·수집 항목·승인 정책을 확정한 것이 아니다.

## 4. 질문 생성 입력 계약 제안

아래 형식을 실험 입력으로 구현했다. 검증 코드는 [schemas.py](schemas.py)에 있다. 이 형식은 팀 DB의 필수 컬럼이나 공개 API 합의 규격이 아니다.

| 필드 | 이번 실험에서의 의미 |
| --- | --- |
| item_id | 샘플 물품 식별자. 운영 환경의 UUID 연결은 백엔드와 협의 |
| category | 물품 종류 문맥 |
| features[].feature_id | 물품 안에서 중복되지 않는 특징 식별자 |
| features[].name | 특징 종류의 설명 |
| features[].value | 확인된 값. 누락은 null로 표시 |
| features[].visibility | public 또는 private. 누가 이 값을 정하는지는 협의 필요 |
| features[].verified | 관찰 근거가 확인되었는지. 모델이 자기 확신으로 설정하는 점수가 아님 |
| features[].distinguishing | 물품을 구별하는 데 쓸 특징인지. 현재는 샘플 작성자가 지정 |

입력 예시에는 합성 데이터만 사용한다.

~~~json
{
  "item_id": "synthetic-wallet-01",
  "category": "지갑",
  "features": [
    {
      "feature_id": "mark",
      "name": "안쪽 각인",
      "value": "HJ-27",
      "visibility": "private",
      "verified": true,
      "distinguishing": true
    }
  ]
}
~~~

실험 코드에서는 공개 특징·불확실한 값·누락된 값·구별력이 없다고 표시한 값을 질문 생성용 특징에서 제외한다. 적합한 특징이 없으면 API 호출 없이 정보 부족으로 처리한다. 이 선별 방식의 적합성은 이후 실제 물품 데이터로 검토해야 한다.

## 5. 질문 결과 계약 제안

~~~json
{
  "status": "ready",
  "questions": [
    {
      "feature_id": "mark",
      "text": "기억나는 각인이나 문구를 설명해 주세요."
    }
  ],
  "reason": "각인에 대한 설명 확인"
}
~~~

위 질문은 형식 설명용 수기 예시이며 실제 Gemini 실행 결과가 아니다.

- `ready`는 질문 생성이 끝났다는 뜻이다. 소유 확인이나 반환 승인을 의미하지 않는다.
- `insufficient_information`은 질문 생성 근거가 부족하다는 뜻이며 질문 목록은 비어 있어야 한다. 소유자 거절로 처리하지 않는다.
- `reason`과 `feature_id`는 내부 검토용이다. 프런트엔드 전달 계약이 확정되기 전 전체 결과를 사용자 화면에 그대로 노출하지 않는다.
- 현재 실험 코드는 질문을 최대 3개로 제한한다. 최종 질문 수나 반복 횟수 정책은 아니다.
- 질문의 영구 ID, 검증 세션 ID, 질문 버전과 답변 연결은 이 파트의 소유 확인 서비스에서 관리한다. 기존 DB와 공통 식별자 규격을 조율한 후 세부 구조를 정한다.

## 6. 구현된 응답 검증과 한계

호출 코드 [gemini.py](gemini.py)에서 다음 항목을 검사한다. 10/14 실행 결과와 발견한 한계는 [실험 결과 검토](experiments/results/question_generation_live_review_20261014.md)에 정리했다.

1. Gemini의 HTTP 200만으로 성공을 판단하지 않는다. 후보 1개와 정상 완료 사유 STOP을 확인한다.
2. 응답을 Pydantic으로 검증한다. 필수 값 누락, 승인 여부 같은 미정 필드, 잘못된 상태, 중복 특징 참조를 거부한다.
3. 질문이 실제로 선별한 특징을 참조하는지 확인한다.
4. 비공개 값 전체가 질문에 포함되면 차단한다. 유니코드 표기·대소문자·공백 차이를 정규화한다.

문자열 검사는 일부 단어만 노출하거나 바꿔 말한 힌트를 완전히 탐지하지 못한다. 실제 호출 후 사람이 질문과 원본 특징을 비교해야 한다. JSON 검증 통과, 기대 상태 일치, 단위 테스트 통과를 질문 품질이나 소유 확인 정확도로 해석하지 않는다.

물품 값 안의 지시문은 데이터로 취급하도록 프롬프트에 명시하고 합성 사례를 준비했다. 프롬프트만으로 모든 지시문 공격을 방어했다고 보장하지 않는다.

## 7. 실험 코드의 오류 처리와 실행 설정

아래 오류 코드는 현재 호출 코드의 내부 구분이다. 팀 API에 전달할 오류 계약과 운영 정책은 별도로 합의한다.

| 내부 오류 | 처리 |
| --- | --- |
| GEMINI_NOT_CONFIGURED | 키·모델 설정 후 다시 실행 |
| AUTHENTICATION_FAILED / MODEL_UNAVAILABLE | 현재 실험 실행 중단, 설정 확인 |
| RATE_LIMITED | 현재 실행 중단. 자동 재시도 없음 |
| INVALID_REQUEST | 요청 형식·설정 확인을 위해 현재 실행 중단 |
| REQUEST_TIMEOUT / NETWORK_ERROR / PROVIDER_ERROR | 실패로 기록. 정상 질문으로 대체하지 않음 |
| CONTENT_BLOCKED / INCOMPLETE_RESPONSE | 차단 또는 잘린 응답을 사용하지 않음 |
| INVALID_RESPONSE / INVALID_FEATURE_REFERENCE | 형식·참조 오류로 기록 |
| ANSWER_LEAK_DETECTED | 질문 사용을 차단하고 프롬프트를 검토 |
| RESPONSE_TOO_LARGE | 응답 읽기를 제한하고 실패 처리 |

오류 코드만 노출하고 제공자 오류 본문이나 키가 포함된 요청 정보를 출력하지 않는다. API 키는 `backend/.env` 또는 환경변수로 읽고 Google API 요청 헤더로 전달한다.

10/14 실험에는 30초 제한, 출력 토큰 4096개, 응답 본문 256 KiB 제한을 적용했다. `gemini-3.5-flash-lite`의 계정 접근과 실제 응답은 해당 실행에서 확인했다. 최종 모델 선정·운영 설정·비용 목표는 미정이다.

| 질문 생성 입력 | 대상 물품과 출처가 확인된 특징을 전달 | 실제 analysis_features와 변환 규칙, 공개·검증 표시 책임 |
| 질문 생성 시점 | 대상 물품이 선택된 뒤 생성하는 안 | 검색 후보 선택, 질문 재생성·재사용, 호출 API |
| 질문·답변 연결 | 이 파트의 서비스가 세션·질문·답변과 상태를 저장·조회 | 기존 DB·ID 규격, 버전·회차·유효기간 |
| 답변 평가 | 원래 특징·질문·사용자 답변을 묶어 AI에 전달하는 안 | 평가 결과 형식, 정보 부족·모순의 처리 |
| 최종 소유 확인 출력 | 이 파트가 평가 결과를 종합해 선재의 백엔드에 전달 | 상태값·판정 기준·추가 확인·판단 보류·실패의 구분과 전달 방식. 현재 미정 |
| 반환 코드 | 백엔드가 합의한 기준으로 발급하는 안 | 승인 근거·최종 판단 주체·재시도·만료 |
| 공개 결과 | 화면에는 합의된 질문·안내만 제공하는 안 | 내부 특징·근거를 숨기는 응답 경계 |

개발용 API와 확인 시도용 DB 마이그레이션은 [워크플로 문서](workflow.md)에 정리했다. 백엔드 `FeatureAnalyzer`는 등록 사진의 특징 추출용이므로 소유 확인 질문 생성기를 그 자리에 연결하지 않는다.
