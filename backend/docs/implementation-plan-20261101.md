# 과거 기록: 2026-11-01 R01

이 문서는 완료된 직렬화 오류 보완 작업의 기록이다. 현재 작업 범위·담당 방식은 [최신 구현 계획](implementation-plan.md)을 따른다.

# 백엔드 구현 계획

작성 기준: **2026-11-01**, `HEAD ac27e81` 및 기존 미커밋 작업 트리.
기준 명세: [ERD](erd.md), [기능 명세](functional-spec.md). 이전 P00~P08 중 등록·촬영·보관 및 내부 검색은 이미 구현되어 있으므로 처음부터 다시 구현하지 않는다.

이번 차수는 **F08 분석 결과 검증의 실패 처리 1건만 보완**한다. 구현은 새 Orca 채팅의 **Claude Opus / high**, 독립 검토는 **gpt-6-astra / medium**으로 진행한다. 모든 작업은 현재 체크아웃에서 수행하며 **commit·push·브랜치 전환·기존 변경 되돌리기를 하지 않는다.**

## 1. 명세와 현재 구현의 연결

| 명세 | 현재 상태 | 이번 차수 |
| --- | --- | --- |
| ERD 8개 테이블·제약 | ORM·최초 마이그레이션 대조 완료 | 스키마·마이그레이션 변경 없음 |
| F01~F07, F12~F13 | 상태 확인·등록·촬영·저장·등록 개방·투입 완료 구현 | 기존 동작 회귀 확인 |
| F08 분석 연결부 | 결과 타입·사진 ID·비어 있지 않은 dict·JSON 직렬화 검증, 실패 시 draft/failed | **결과 검증 중 직렬화 깊이 오류 처리 보완** |
| F09 질문 생성 | Gemini 실험 코드, 업무 API/DB 미연결 | 이번 구현 대상 아님 |
| F10~F11 및 수령 | 반환 코드·수령 미구현, 계약 미정 | 구현하지 않음 |
| 실제 이미지 AI·공개 검색·인증·복구 | 계약·정책·외부 환경이 필요한 후속 작업 | 임의로 확정하지 않음 |

이 계획의 보류 항목은 실패를 숨기거나 정상 응답으로 대체하라는 의미가 아니다. 기존 명세가 허용한 API·상태·오류 코드만 사용한다.

## 2. 이번에 확인한 문제

근거: 기능 명세 F08의 `allow_nan=False` JSON 직렬화 검사와 ERD의 분석 실패 상태.

수정 전 `services.analyze()`는 결과의 `features`를 JSON 직렬화할 때 `ValueError / TypeError`를 `INVALID_ANALYSIS_RESULT`로 변환했다. 그러나 과도하게 중첩된 dict에서 발생한 `RecursionError`는 빠져나갔다.

2026-11-01 기존 SQLite·가짜 Pi/S3 테스트 구성에서 다음을 재현했다.

1. 사진 두 장을 저장한 등록에 10,000단계로 중첩된 특징 dict를 반환하는 분석기를 사용했다.
2. 분석 요청에서 `RecursionError`가 발생했다.
3. DB에는 등록 `analyzing`, 분석 `running`이 남았다.
4. 같은 등록의 명시적 분석 재요청은 409 `INVALID_REGISTRATION_STATE`로 막혔다.

이 입력은 실제 AI 모델의 품질 문제가 아니라 백엔드 결과 직렬화 검증 경계의 문제다. 분석기 내부 임의 오류·DB 장애·프로세스 중단 전반의 자동 복구를 이번에 추가하지 않는다.

## 3. 구현 작업 R01

### R01-1: 직렬화 검증 오류 처리

- `backend/app/services.py`의 분석 결과 JSON 검증에서 재귀 깊이 초과도 기존 `INVALID_ANALYSIS_RESULT`로 처리한다.
- 기존 오류 경로로 HTTP 502, 등록 `draft`, 분석 `failed`, 특징 비우기를 적용한다.
- 사진 2장과 분석 입력 ID 스냅샷을 보존하여 사용자가 정상 분석을 명시적으로 재요청할 수 있게 한다.
- `except Exception`으로 분석기·DB·프로세스 오류를 모두 숨기지 않는다. 직렬화 검사 범위에 한정한다.
- 별도 최대 깊이 정책, 새 의존성, 새 API·오류 코드·상태·추상 계층을 만들지 않는다.

### R01-2: 의미 있는 회귀 검증

기존 테스트의 미커밋 변경을 보존하면서 아래 사례를 검증한다. 새로 추가한 재귀 오류 사례는 수정 전 코드에서 실패함을 확인한다.

| 사례 | 기대 결과 |
| --- | --- |
| 비어 있거나 dict가 아닌 특징 | 기존 502 `INVALID_ANALYSIS_RESULT`, draft/failed |
| JSON 비지원 값·NaN/Infinity·순환 참조 | 같은 검증 실패 경로 |
| 직렬화 가능한 깊이를 초과한 중첩 dict | 500/예외 누출·진행 상태 고착 대신 같은 검증 실패 경로 |
| 검증 실패 직후 개방 요청 | 개방 거절, 보관함 명령 없음 |
| 검증 실패 후 정상 결과로 분석 재요청 | 같은 등록·사진으로 ready/succeeded, 기존 사진 보존 |
| 정상 분석 및 ready 상태의 중복 분석 | 정상 성공과 기존 결과 재사용 유지 |
| 분석기 자체의 예기치 않은 오류 | 포괄적인 예외 처리로 정상·복구 성공인 것처럼 바꾸지 않음 |

기존에 충분히 검증하는 사례를 중복 작성하지 않는다. 깊이 사례는 재귀로 테스트 데이터를 만들지 말고 반복문으로 생성하며, 필요하면 직렬화 한계를 확인해 런타임 차이에 견디도록 작성한다.

### R01-3: 명세와 검증 기록 반영

- 기능 명세 F08에 이번에 처리하는 결과 직렬화 오류 범위만 명확히 한다.
- 새 테이블이나 새 업무 기능이 완성됐다고 표시하지 않는다.
- 이번 결과는 2026-11-01 기록으로 추가하고 10/31의 테스트 결과·기존 작업 트리 기준은 보존한다.

## 4. 작업 소유권과 변경 경계

| 역할 | 책임 |
| --- | --- |
| 현재 조정자 | 구현 계획 작성·작업 전달·결과 취합·최종 검증 |
| Claude Opus high 새 Orca 채팅 | R01 코드·테스트·최소 명세 수정, 필요 시 검토 지적 수정 |
| Astra medium 별도 Orca 채팅 | 계획 준수·명세 정합성·회귀·오류 처리 범위를 독립 검토. 코드 직접 수정 없음 |

구현 허용 파일은 `backend/app/services.py`, `backend/tests/test_registration.py`(기존 변경 보존), 필요한 경우 작은 분석 검증 전용 테스트 파일, `backend/docs/functional-spec.md`의 관련 부분이다. 구현 계획의 진행 기록은 조정자가 관리한다.

금지 범위: 모델 선정·실제 Gemini/S3/Pi 호출, F09 질문/답변 API 신설, 소유 확인·반환 승인 정책, DB/마이그레이션 변경, 새 인증·재촬영·예약 해제·전반적인 예외 복구, 무관한 리팩터링. `.env`·비밀값을 읽거나 출력할 필요가 없다.

## 5. 완료 기준과 실행 순서

1. **계획·재현 완료:** 위 R01 범위와 기존 오류를 확인한다.
2. **Opus 구현:** 최소 변경과 실패→정상 재요청 회귀 테스트를 작성한다.
3. **Astra 검토:** 최종 변경분만 독립적으로 검토하고, 중요도·파일/행·재현 또는 논리 근거를 보고한다.
4. **지적 처리:** 수정이 필요하면 Opus에 전달하고 수정된 범위를 Astra가 다시 확인한다.
5. **최종 검증:** 관련 테스트와 전체 백엔드, 기존 루트 종단 테스트, `git diff --check`를 실행한다. 단계별로 이미 통과한 검증은 새 변경이나 미확인 문제가 있을 때만 다시 실행한다.
6. **결과 전달:** 실제 모델/effort·Orca 채팅·변경 파일·검증 결과·남은 제한을 보고한다. commit·push는 하지 않는다.

PowerShell 기준:

```powershell
Push-Location backend
& ..\.venv\Scripts\python.exe -m pytest -q -ra
Pop-Location
& .\.venv\Scripts\python.exe -m pytest -q -ra
git diff --check
```

PostgreSQL 전용 동시성 테스트는 별도 테스트 DB가 없으면 건너뛰고 이유를 기록한다. 이번 범위에서는 실장치·AI 품질·운영 DB 검증을 완료로 주장하지 않는다.

## 6. 진행 기록

- 2026-11-01: 최신 명세·코드 대조 및 과도한 중첩 특징으로 인한 상태 고착 재현 완료.
- Astra medium 사전 검토: F08·ERD와 R01 범위의 정합성 및 기존 상태 고착을 독립 확인했다.
- Opus high 구현 완료: JSON 직렬화 검사에만 `RecursionError` 처리를 추가하고, 잘못된 특징 8개 사례와 분석기 내부 오류 1개 사례를 검증했다. 실제 Orca 실행의 요청/적용 모델은 `claude / opus / high`, 구현 dispatch는 `ctx_e06b3e65a3ab`이다.
- 구현자 검증: 관련 테스트 **11 passed**, 전체 백엔드 **88 passed, 3 skipped**. 별도 임시 사본에서 수정 전 코드의 깊이 테스트 실패와 잘못된 광범위 예외 처리의 경계 테스트 실패를 확인했다.
- 조정자 검증: 기존 루트 종단 테스트 **5 passed**. 기존 사용자 변경·ERD·루트 테스트는 작업 전 사본과 대조해 보존을 확인했다. `HEAD ac27e81` 유지, staging·commit·push 없음.
- 최종 독립 검토 완료: 새 Orca 채팅의 요청/적용 모델 `codex / gpt-6-astra / medium`, dispatch `ctx_ae05a6512cfd`. 명세·범위·회귀 검토에서 차단 이슈 없음. 별도 사본에서 관련 테스트 **13 passed**, 수정 전 코드에서 깊이 테스트 실패를 독립 확인했다.
- 검토 지적 반영: Opus high(`ctx_74b70efff958`)가 깊이 테스트 주석의 부정확한 설명과 기능 명세의 확인일 표현을 정정했다. Astra medium(`ctx_8ff4b531be97`) 재검토에서 두 항목 해결 및 검토 당시 대비 백엔드 Python 21개 파일의 AST 동일성을 확인했다. 실행 코드 변경이 없어 테스트를 중복 실행하지 않았다.
- **R01 완료:** 코드·회귀 테스트·F08 명세 반영, 독립 검토와 지적 정정까지 완료했다. `git diff --check` 통과. PostgreSQL 전용 3개 테스트, 실장치 및 실제 AI 품질은 이번 검증 범위 밖이다.
