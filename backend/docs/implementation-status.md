# 백엔드 구현 현황

2026-10-12. 기존 2026-10-08 문서는 설계 검토 당시 기록이다. 현재 동작은 이 문서와 [로컬 API 계약](../../docs/api.md), 코드·테스트를 기준으로 확인한다.

## 이번 사용자 결정

- D10: 등록 생성·촬영·분석·개방·완료를 별도 API로 구현하고 UUID·상태·중복 배정 방지 구조를 채택한다.
- D11: 이번 범위는 등록·촬영·보관·검색 준비까지이다. AI는 교체 가능한 연결부와 테스트로 준비한다. 소유 확인·반환 코드·수령은 보류한다.
- D12: 카테고리 필수 여부와 공개 범위는 아직 확정하지 않는다. 등록 입력은 선택값으로 저장하고 검색은 내부 서비스까지만 구현한다. 공개 검색 API는 보류한다.
- D13: 업무 API는 기본 비활성화하고 명시적인 로컬 개발 설정에서만 활성화한다. 실제 장치·공개 배포 전 인증은 별도로 연결한다.

## 구현된 범위

| 작업 | 구현과 검증 범위 |
| --- | --- |
| P00 | FastAPI 의존성 교체, 테스트 전용 Pi·저장소·AI, 정상/실패 시나리오. 실행 앱에는 가짜 AI를 등록하지 않음 |
| P01 | 키오스크·카테고리 조회, 선택 입력 등록 생성/조회, UUID·FK·상태 제약, 명시적 로컬 시드 |
| P02 | 순차 촬영 2회, JPEG 디코딩·크기 검증, 비공개 S3 어댑터, 객체 키/메타데이터 저장, 임시 미리보기 URL |
| P03 | 두 사진 바이트/ID를 AI 경계로 전달, 결과 대상·순서·특징 JSON 검증, 결과 저장. 실제 AI 성공 스키마는 미정 |
| P04 | 분석 성공 및 사진 일치 확인, 빈 칸 원자적 예약, 명령 선저장, Pi opened 검증, 완료 확인+closed, 중복 요청 억제 |
| P05 | 로컬 키오스크 위치 조회. 보관 완료 물건의 내부 필터·페이지네이션. 공개 검색 경로 없음 |
| P06~P08 | 소유 확인·반환 및 실제 시스템 통합은 이번 범위에 포함하지 않음 |

DB는 `kiosks/categories/lockers/registrations/item_images/device_commands/found_items/storage_assignments` 8개 테이블이다. AI 특징은 등록의 `analysis_features` JSONB에 원본 입력과 구분해 저장한다. 별도 `devices/item_features/verification_attempts/return_codes` 테이블은 아직 필요하지 않아 추가하지 않았다. 분석 입력 ID는 서비스에서 검사하며 JSON 내부 참조를 FK로 보호하지는 않는다.

장치 주소는 이번 로컬 구현에서 `PI_DEVICES` 설정으로 전달한다. Pi 내부 경로에는 보관함 UUID가 아닌 키오스크 안의 정수 `locker_number`를 사용한다. 물건·칸의 유효 배정은 부분 UNIQUE 인덱스로 중복을 방지한다. 배정 선택에는 PostgreSQL 키오스크 행 잠금으로 가용성 조회를 직렬화하고, 칸 행 잠금과 `SKIP LOCKED`를 함께 사용한다. 외부 호출 전에 트랜잭션을 종료하므로 Pi 응답을 기다리는 동안 배정 잠금을 유지하지 않는다.

## 합의 전 보수적으로 유지하는 제한

- 재촬영·사용자 취소·예약 만료·자동 해제·하드웨어 재시도는 구현하지 않았다. 명확한 개방 실패도 배정을 보존한다. 응답 유실은 `unknown`, 명시적 장치 실패는 `failed`로 남긴다.
- 외부 작업 전 등록 진행 상태와 명령을 커밋한다. 프로세스/DB 장애로 결과를 기록하지 못하면 진행 상태와 `sent`가 남아 재실행을 막는다. 이 상태를 정상/빈 칸으로 자동 간주하지 않는다.
- S3 업로드 성공 후 DB 기록에 실패하면 명령 ID로 된 객체가 남을 수 있다. 자동 삭제·보존 기간은 Q07/Q11 합의 전 미구현이다. 복구 시 등록/명령/배정과 실제 장치를 함께 대조해야 한다. 임의 DB 초기화나 새 개방 명령으로 복구하지 않는다.
- 분석 실패는 촬영 이미지가 유지된 `draft`로 돌아가 명시적 분석 재요청이 가능하다. 프로세스 중단으로 남은 `analyzing`은 자동 해제하지 않는다.
- 작은 칸 번호 우선, 2,000자 입력 제한, 내부 검색 limit 20/최대 100은 로컬 구현 선택이며 최종 정책 확정이 아니다. 명령 TTL·HTTP 시간 제한·이미지 크기·서명 URL 만료는 설정 없이는 해당 연동을 사용하지 못한다.
- 실제 Pi·S3·AI 연결, 공개 인증, CORS/FE 배포 출처, 재시도/복구/보존, 최종 카테고리·공개 검색 계약은 후속 합의가 필요하다.

## 검증 방법

`backend`에서 `python -m pytest -q`로 장치 없는 테스트를 실행한다. SQLite는 빠른 흐름 검증용이다. PostgreSQL의 동시성은 별도로 `TEST_DATABASE_URL`을 지정해 같은 테스트와 병렬 배정 검증을 실행한다. 이 옵션은 테스트마다 임의 이름의 전용 스키마를 생성하고 그 스키마만 정리한다. 별도 테스트 DB 사용을 권장한다.

```powershell
$env:TEST_DATABASE_URL='postgresql+psycopg://user:password@127.0.0.1:5432/test_database'
python -m pytest -q
```

테스트는 미합의 정책의 승인이나 실제 장치 통합 완료를 의미하지 않는다.

2026-10-12 검증: 별도 PostgreSQL 17에서 35개 테스트 통과. 서로 다른 등록의 동시 배정, 같은 등록의 동시 개방·완료, 실제 개방 후 DB 결과 기록 실패, 마이그레이션 upgrade/downgrade와 ORM 일치를 확인했다. Alembic CLI의 `upgrade head` 및 `check`, 로컬 시드 반복 실행의 중복 방지도 통과했다. Pi·S3·AI는 모의 연결이며 실제 네트워크 통합 검증은 포함하지 않는다.

같은 날 후속 검증: 등록·조회 기본 테스트 3개와 Docker 테스트 경로 설정을 추가해, Docker/Python 3.12/PostgreSQL 17에서 총 38개 테스트가 통과했다. 등록·조회 커밋 단계는 7개, 촬영·분석 커밋 단계는 19개 테스트로 독립 실행을 확인했다. Swagger에서 직접 테스트하는 순서는 [백엔드 README](../README.md)에 안내한다.
