# 이미지 분석 및 특징 추출

스마트 분실물 보관함의 등록 사진을 분석하여 물품의 특징을 추출하는 파트이다. 담당 범위, 검토 중인 분석 방식, 실험에서 확인한 문제와 다른 파트의 협의 항목을 이 폴더에서 관리한다.

현재는 설계 초안이며, **Qwen 계열 VLM을 사용할지 Gemini API로 이미지 분석을 수행할지는 결정하지 않았다.** 개인 로컬 시제품에서 사용한 모델이나 출력 형식을 팀의 최종 규격으로 간주하지 않는다. 이 폴더에는 우선 README만 추가한다.

## 1. 목적과 담당 범위

분실물 사진에서 물품의 종류와 구별되는 특징을 추출하고, 백엔드가 저장·연결하여 검색 및 소유 확인 파트에서 활용할 수 있는 구조화된 결과를 제공한다.

담당 범위는 다음과 같다.

- 이미지 분석에 필요한 입력 및 최소 전처리 검토
- 습득자가 선택한 카테고리를 활용한 분석
- 물품 특징 추출과 결과 형식 검증
- 촬영 방향·품질에 따른 특징 추출 결과 비교
- 분석 실패나 확인하기 어려운 특징의 표현 방식 검토

카메라 촬영과 장치 제어는 Raspberry Pi 파트, 등록 업무와 이미지·결과 저장은 백엔드 파트가 맡는 방향이다. 추출한 특징을 이용한 질문 생성과 답변 평가는 소유 확인 파트와 협의한다.

## 2. 현재 방향과 미정 사항

| 항목 | 상태 | 내용 |
| --- | --- | --- |
| 파트 목표 | 개발 목표 | 분실물 사진에서 특징을 추출해 구조화된 결과 제공 |
| 습득자 입력 | 파트 개발 방향 | 물품 카테고리만 전달하고 상세 notes 입력은 요구하지 않음. 팀 UI와 입력 계약은 협의 필요 |
| 촬영 구성 | 팀 촬영 설계 | 카메라 1대로 물건 방향을 바꿔 등록당 사진 2장 촬영 |
| 이미지 분석 방식 | 미정 | Qwen 계열 VLM과 Gemini API를 후보로 비교 |
| 모델·실행 환경 | 미정 | 구체적인 모델, 실행 위치, 배포 및 운영 방식 |
| 두 사진의 분석 | 미정 | 함께 분석할지 각각 분석 후 결과를 통합할지 검토 |
| 특징 결과 | 후보 검토 | 종류·색상·재질·브랜드·문구·구별되는 특징·요약 설명 |
| 팀 입출력 규격 | 미정 | 이미지 전달 방식, 카테고리 코드, 필드명·타입·필수 여부, 오류 형식 |
| 분석 성공 기준 | 미정 | 필요한 특징과 품질, 확인 불가 결과, 재촬영·실패 처리 조건 |

소유 확인 파트의 Gemini 사용 결정과 이미지 분석 파트의 모델 선택은 별도 결정이다.

## 3. 처리 흐름의 초안

```text
분실물 사진과 습득자가 선택한 카테고리
    → 이미지 확인 및 필요한 최소 전처리
    → 선택한 이미지 분석 모델에 입력
    → 관찰 가능한 특징 추출
    → 구조화된 결과의 형식 검증
    → 백엔드에 분석 결과 전달
```

카테고리는 외형이 비슷한 물품을 구분하는 문맥으로 활용한다. 사용자 입력과 모델이 사진에서 판단한 결과의 출처를 구분하고, 둘이 불일치할 때 어떤 값을 사용할지는 팀과 정한다. 카테고리만으로 재질·브랜드·부착물 등의 특징을 추측하지 않도록 검토한다.

팀 촬영 설계는 두 사진을 전제로 한다. 현재 개인 로컬 실험은 단일 사진으로 진행했으며, 두 사진의 분석과 통합 방식은 후속 검토 대상이다. 촬영 각도와 해상도·화질은 실제 결과를 비교한 뒤 Pi 및 프런트엔드 담당자와 정한다.

## 4. 추출할 특징의 후보

아래는 비교 실험을 위한 후보이며 최종 API나 DB 스키마가 아니다.

| 특징 | 검토 내용 |
| --- | --- |
| 물품 종류 | 습득자 선택 카테고리와 사진에서 판단한 종류 |
| 색상 | 물품에서 관찰되는 주요 색상 |
| 재질 | 사진에서 확인 가능한 재질과 확인하기 어려운 경우의 표현 |
| 브랜드 | 식별 가능한 브랜드 표기 |
| 보이는 문구 | 사진에 실제로 적힌 글자·숫자 |
| 구별되는 특징 | 부착물, 무늬, 형태, 흠집 등 물품을 구분할 근거 |
| 요약 설명 | 확인된 특징을 일관되게 정리한 설명 |

불확실한 특징을 임의로 채우지 않는 방향으로 검토한다. 확인 불가·누락을 나타내는 값과 필수 특징은 백엔드 및 소유 확인 파트와 협의한다. JSON 형식 검증 통과와 특징 내용의 정확성은 구분하여 평가한다.

## 5. 현재까지의 검토와 비교 계획

개인 로컬 시제품에서 Qwen을 이용한 단일 사진 분석과 카테고리 힌트 전달을 시험했다. 물품 종류·재질·부착물을 잘못 판단하는 사례와 프롬프트 예시의 특징을 따라 생성하는 사례를 관찰했다. 모델 출력이 기대한 JSON 타입과 다르게 생성되는 경우도 있었다.

프롬프트와 결과 검증을 보완하고 카테고리를 함께 전달하는 방식을 검토했지만, 제한된 사진의 결과만으로 일반적인 정확도나 최종 모델을 확정하지 않는다. Gemini API를 이용한 이미지 분석의 비교 실험은 아직 수행하지 않았다.

다음 비교에서는 동일한 물품 사진과 카테고리를 사용한다.

- 물품 종류와 구별되는 특징이 사진과 일치하는지
- 사진에 없는 특징이나 불확실한 재질을 생성하는지
- 브랜드와 한글·영문 문구를 정확히 읽는지
- 단일 사진과 서로 다른 방향의 두 사진에서 결과가 어떻게 달라지는지
- 결과 형식의 안정성, 실패 처리와 반복 결과의 일관성
- 처리 시간, 실행·운영 부담 및 API 사용 비용

평가용 사례에는 기대 결과와 판단 근거를 먼저 기록한다. 비교 결과를 바탕으로 분석 방식과 필요한 특징을 선택하며, 목표 수치와 통과 기준은 아직 정하지 않았다.

## 6. 다른 파트와 협의할 내용

| 파트 | 협의 항목 |
| --- | --- |
| 프런트엔드 | 카테고리만 입력하는 방향, 카테고리 목록·표시명·코드, 두 촬영 사이의 방향 안내, 재촬영 안내 |
| Raspberry Pi | 두 사진의 촬영 방향, 해상도·화질·초점, 분석에 필요한 촬영 조건 |
| 백엔드 | 사진 두 장과 등록 건의 연결, 이미지 전달 방식, 분석 호출 시점, 결과 검증·저장, 실패·재시도 |
| 소유 확인 AI | 필요한 특징, 사용자 입력과 AI 추출 정보의 구분, 확인 불가 정보의 활용, 특징의 공개 범위 |

현재 프런트 문서에는 사용자가 추가 특징을 입력하는 방향이 남아 있어 카테고리만 입력하는 방안과 조율이 필요하다. 또한 백엔드 검토 문서에는 분석 성공 후 등록용 보관함을 개방하는 방향이 기록되어 있으므로, 분석 성공의 의미와 오류 처리를 함께 정해야 한다.

파트 간 합의된 규격은 팀 저장소의 공통 `docs/`에 반영하고 이 문서에서 연결한다. 이 초안만으로 API·DB·보관함 개방 조건을 확정하지 않는다.
