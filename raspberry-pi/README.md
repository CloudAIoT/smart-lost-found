# smart-lost-found Raspberry Pi

키오스크 현장의 하드웨어를 제어하는 라즈베리파이 파트. 라즈베리파이 두 대를 쓴다. 촬영 Pi는 촬영 상자의 카메라를, 보관함 Pi는 보관함의 잠금장치와 문 센서를 맡는다. 두 Pi 모두 백엔드의 명령을 받아 하드웨어를 움직이고, 결과를 백엔드에 돌려준다.

현재 두 Pi에 컨트롤러를 설치해 Tailscale로 백엔드(EC2)와 연결했다. 촬영 Pi는 실제 카메라로 찍고, 보관함 Pi는 잠금장치 대신 칸마다 LED와 버튼으로 동작을 보여 준다([결정 기록 0002](docs/decisions/0002-locker-led-button.md)). 백엔드와 주고받는 요청·응답은 [docs/device-protocol.md](../docs/device-protocol.md)에 정리했다.

## 구성

| Pi | 연결 장치 | 하는 일 |
| --- | --- | --- |
| 촬영 Pi | 카메라 1대(Camera Module 3) | 분실물 촬영(방향을 바꿔 2장) |
| 보관함 Pi | 칸마다 LED와 버튼 (시제품, 잠금장치·문 센서는 향후 과제) | 열린 칸 표시, 문 닫힘 확인 |

사진을 2장 찍는 이유: 물건의 한 면만 찍으면 모양·크기·특징을 정확히 판별하기 어렵다. Raspberry Pi 4에는 카메라 단자가 하나뿐이라, 카메라 1대로 한 장을 찍은 뒤 사용자에게 물건을 돌리거나 눕혀 달라고 안내하고 한 장을 더 찍는다.

Pi를 두 대로 나눈 이유: 촬영 상자 쪽에는 카메라와 모니터·키보드·마우스를, 보관함 쪽에는 잠금장치와 문 센서를 연결한다. 촬영 상자와 보관함의 위치에 따라 한 대로는 배선이 어려울 수 있어 두 대로 나눴다. 두 Pi는 같은 프로그램을 쓰고 설정으로 역할을 나눈다. 2026-11-18부터 키오스크 화면은 아이패드로 띄우므로 촬영 Pi에는 카메라만 연결한다([결정 기록 0005](docs/decisions/0005-kiosk-ipad.md)).

## 시스템에서의 위치

```mermaid
flowchart LR
    Screen[키오스크 웹 화면, 아이패드] -->|HTTPS| Backend[백엔드 API 서버]
    Backend -->|촬영 명령| CapturePi[촬영 Pi]
    CapturePi -->|사진| Backend
    Backend -->|개방 명령| LockerPi[보관함 Pi]
    LockerPi -->|처리 결과| Backend
    CapturePi --- Camera[카메라]
    LockerPi --- Locker[칸별 LED·버튼]
```

백엔드와 두 Pi는 Tailscale로 연결된다. 키오스크 웹 화면은 촬영 상자 옆 아이패드에 띄우고, 화면은 Pi의 API를 직접 부르지 않고 백엔드하고만 통신한다. Pi도 백엔드를 주기적으로 조회하지 않는다.

## 하드웨어 구성 (시제품)

- 촬영 상자 1개: 카메라 1대(Raspberry Pi Camera Module 3, 자동초점). 분실물을 넣고 '촬영'을 누르면 한 장, 물건을 돌리거나 눕힌 뒤 한 장을 더 찍는다
- 보관함 2칸: 칸마다 LED(열린 칸 표시)와 버튼(문 닫힘). 잠금장치와 문 센서는 향후 과제다
- 아이패드: 촬영 상자 옆에서 배포된 웹의 키오스크 화면을 띄운다 (터치)

상자 크기, 장치 위치, 배선은 [하드웨어 설계](hardware/README.md)에 3D 모델로 정리했다.

## 실행 방법 (개발용 가짜 하드웨어)

```bash
cd raspberry-pi
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env    # PI_ROLE과 PI_API_KEY를 정한다
uvicorn --factory app.main:create_app --host 127.0.0.1 --port 8001
pytest -q               # 테스트
```

`PI_FAKE_HARDWARE=true`이면 실제 장치 없이 동작한다. 촬영 요청에는 번호와 시각이 적힌 샘플 JPEG를 돌려주고, 보관함을 열면 문이 `PI_FAKE_DOOR_OPEN_SECONDS`초 동안 열려 있다가 닫힌 것으로 보인다. 같은 `command_id`가 다시 오면 만료 여부와 상관없이 처음 결과를 돌려주고, 새 명령만 만료 시각을 검사한다.

## 실제 카메라 (촬영 Pi)

촬영 Pi에서 `PI_FAKE_HARDWARE=false`로 실행하면 Camera Module 3로 찍는다. Pi에 설치하고 전원을 켜면 저절로 실행되게 하는 방법은 [설치와 접속 7절](deploy/setup.md#7-컨트롤러-설치와-자동-실행)에 있다.

- 서버가 켜질 때 카메라를 켜 두고, 촬영 요청마다 초점을 한 번 맞춘 뒤 찍는다([실험 0001](docs/experiments/0001-camera-first-test.md)의 방식 A).
- 초점 맞추기는 `PI_FOCUS_TIMEOUT_SECONDS`(기본 3초)를 넘으면 멈추고, 초점이 덜 맞은 채로라도 찍는다. 사진 대신 오류를 돌려주는 것보다 다시 찍을 수 있는 사진을 주는 편이 낫다고 봤다.
- 사진 크기는 기본 2304×1296(`PI_CAPTURE_WIDTH`, `PI_CAPTURE_HEIGHT`)이다. 이미지 분석이 사진의 긴 변을 1280px로 줄여 쓰므로 최대 해상도(4608×2592)는 필요 없다.
- 촬영 중 오류가 나면 카메라를 닫고 다음 요청에서 다시 연다. 케이블을 다시 꽂아도 서버를 재시작하지 않아도 된다.

2026-11-13 촬영 Pi에서 확인했다. 촬영 요청 5번 모두 2304×1296 JPEG(약 370~400KB)가 왔고, 요청부터 사진을 받기까지 0.42~0.50초 걸렸다. 맥에서 SSH 터널로 백엔드의 `PiGateway`와 JPEG 검사 함수로 받아 봤을 때도 통과했다(0.6~0.7초).

## 보관함 LED·버튼 (보관함 Pi)

보관함 Pi에서 `PI_FAKE_HARDWARE=false`로 실행하면 칸마다 LED와 버튼을 쓴다([결정 기록 0002](docs/decisions/0002-locker-led-button.md)).

- 개방 명령을 받으면 그 칸의 LED가 깜빡인다. 문 상태는 `open`이 된다.
- 물건을 넣거나 꺼낸 뒤 그 칸의 버튼을 누르면 문이 닫힌 것으로 보고 LED가 꺼진다. 문 상태는 `closed`가 된다.
- 닫혀 있는 칸의 버튼은 눌러도 아무 일도 없다.

키트의 브레드보드와 T자 확장보드로 연결한다. 핀 번호는 바꿀 수 있다(`PI_LOCKER_LED_PINS`, `PI_LOCKER_BUTTON_PINS`).

| 칸 | LED | 버튼 |
| --- | --- | --- |
| 1번 | GPIO 17 (11번 핀) | GPIO 22 (15번 핀) |
| 2번 | GPIO 27 (13번 핀) | GPIO 23 (16번 핀) |

- LED: GPIO → LED의 긴 다리, LED의 짧은 다리 → 저항(220~330Ω) → GND. 저항은 LED 앞뒤 어디에 있어도 된다
- 버튼: 브레드보드 가운데 홈에 걸쳐 꽂고, 대각선으로 마주 보는 두 다리를 GPIO와 GND에 연결한다. 버튼 안에서 늘 이어져 있는 다리가 있어서, 홈 한쪽에만 꽂으면 누르지 않아도 연결될 수 있다. Pi 안의 풀업 저항을 써서 저항이 따로 필요 없다

2026-11-17 보관함 Pi에서 확인했다. 자동 실행 서비스(가짜 모드)는 그대로 두고 시험용으로 실제 모드를 따로 띄워 1번, 2번 칸을 차례로 열었다. 열린 칸의 LED가 깜빡이다가 그 칸의 버튼을 누르면 꺼지고, 문 상태가 `closed`로 바뀌었다. 위쪽 버튼으로 1번 칸이 닫힌 것으로 리본 케이블 방향도 맞는 것을 확인했다.

| 1번 칸을 열었을 때 | 2번 칸을 열었을 때 |
| --- | --- |
| ![1번 칸을 열어 초록 LED가 켜진 모습](hardware/photos/locker-led-1.jpg) | ![2번 칸을 열어 빨간 LED가 켜진 모습](hardware/photos/locker-led-2.jpg) |

1번 칸은 초록 LED, 2번 칸은 빨간 LED다. 오른쪽 사진은 1번 칸 버튼을 눌러 초록 LED가 꺼진 뒤 2번 칸을 연 모습이다.

시연할 때는 물건을 넣거나 꺼낸 뒤 그 칸의 버튼을 먼저 누르고 화면에서 완료를 누른다. 백엔드는 보관·수령을 완료하기 전에 문 상태를 확인하므로([D03·D06](../backend/docs/spec-review.md)), 버튼을 누르지 않으면 `DOOR_NOT_CLOSED`로 완료되지 않는다.

## 백엔드 호출 코드로 확인

가짜 모드로 촬영 Pi와 보관함 Pi를 각각 띄운다(키는 예시).

```bash
PI_ROLE=capture PI_API_KEY=capture-key-123 PI_FAKE_HARDWARE=true uvicorn --factory app.main:create_app --port 8001
PI_ROLE=locker PI_API_KEY=locker-key-123 PI_FAKE_HARDWARE=true uvicorn --factory app.main:create_app --port 8002
```

2026-10-26 확인(2026-10-28 재확인): 백엔드가 Pi를 부를 때 쓰는 코드(`backend/app/integrations.py`의 `PiGateway`)로 두 서버를 불러 9가지를 확인했고 모두 기대한 결과가 나왔다. 확인한 것은 촬영 2회(백엔드 JPEG 검사 통과), 보관함 개방, 개방 직후와 잠시 뒤의 문 상태(open → closed), 오류 4가지(만료된 명령, 없는 보관함, 틀린 API 키, 촬영 주소에 보관함 Pi를 넣은 경우)이다.

2026-11-13에는 두 Pi에 설치한 컨트롤러(가짜 모드)를 같은 방법으로 불러 9가지 모두 통과했다. 같은 날 백엔드 담당이 백엔드에서 Tailscale 너머의 실제 Pi를 부르는 종단 테스트와, 실제 Pi·S3로 등록 흐름을 손으로 확인하는 절차를 추가했다([루트 README](../README.md), #21).
