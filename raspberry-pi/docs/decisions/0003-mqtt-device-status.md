# 0003. 물건 유무와 장치 상태는 MQTT로 알린다

- 날짜: 2026-11-15
- 상태: 제안 (팀 협의 전)

## 배경

2026-10-28 SAD 발표에서 교수님께서 MQTT 같은 실제 AIoT 프로토콜을 적용해 보면 좋겠다고 하셨다. 강의자료 「AIoT 시스템의 구조와 센서 기술」 9번 슬라이드의 구조도에서도 라즈베리파이 같은 엣지 장치의 센서 데이터가 클라우드 계층의 MQTT 브로커를 거쳐 API 서버와 대시보드로 간다.

지금은 백엔드가 필요할 때만 Pi에 HTTP로 요청한다(촬영, 개방, 문 상태 조회). 그래서 백엔드가 묻기 전에 Pi 쪽에서 생긴 변화는 알 수 없다. 보관 중인 칸에서 물건이 없어지거나 Pi 전원이 꺼져도 다음 요청을 보낼 때까지 모른다.

## 조사한 내용

### MQTT

MQTT에서는 장치가 브로커(중계 서버)에 주제(topic)를 붙여 메시지를 발행하면, 그 주제를 구독한 쪽이 메시지를 받는다. 보내는 쪽과 받는 쪽이 서로의 주소를 몰라도 된다. 이 프로젝트에 쓸 만한 기능은 다음과 같다([MQTT 3.1.1 표준](https://docs.oasis-open.org/mqtt/mqtt/v3.1.1/os/mqtt-v3.1.1-os.html)).

- 보존 메시지(retain): 브로커가 주제마다 마지막 메시지를 기억했다가 나중에 구독한 쪽에도 보내 준다. 백엔드가 다시 켜져도 칸마다 지금 물건이 있는지 바로 알 수 있다.
- 유언 메시지(Will): 장치가 접속할 때 브로커에 맡겨 두는 메시지다. 장치가 정상 종료 없이 끊기면(전원 꺼짐, 네트워크 끊김, 응답 없음) 브로커가 대신 발행한다. Pi가 꺼진 것을 바로 알 수 있다.
- QoS: 전달 보장 수준이다. 0은 최대 한 번, 1은 최소 한 번, 2는 정확히 한 번 전달한다.

### 쓸 곳

| 후보 | 내용 | 쓸모 |
| --- | --- | --- |
| 칸의 물건 유무 | 칸마다 센서를 달아 물건이 들어오거나 나갈 때 알린다 | 보관 중인 칸이 비면 경고한다(분실·도난 의심). 비어 있어야 할 칸에 물건이 있으면 배정 전에 확인한다 |
| 촬영 상자의 물건 유무 | 촬영 상자에 물건이 놓였는지 알린다 | 화면이 상황에 맞게 물건을 넣으라고 안내하거나 촬영 버튼을 보여 준다. 촬영 뒤 물건이 남아 있으면 보관함으로 옮기라고 안내한다 |
| 장치 연결 상태 | Pi가 접속하면 `online`, 끊기면 브로커가 유언 메시지로 `offline`을 발행한다 | 관리 화면에 장치 상태를 보여 준다. 꺼진 키오스크에는 명령을 보내기 전에 안내할 수 있다 |
| 문 열림·닫힘 | 칸의 문 상태가 바뀔 때 알린다 | 문이 오래 열려 있으면 알린다 |

### 물건 감지 센서

처음에는 칸과 촬영 상자 바닥에 압력 센서를 깔아 물건이 있는지 보려 했다. 쓸 수 있는 센서를 비교하면 다음과 같다.

| 센서 | 판단 |
| --- | --- |
| 압력 센서(FSR) | 값이 아날로그로 나오는데 Pi에는 아날로그 입력이 없어 변환 칩(ADC)을 사야 한다. 카드처럼 가벼운 물건은 잡히지 않을 수 있다 |
| 무게 센서(로드셀과 HX711) | 정확하지만 사야 하고, 칸마다 받침 구조를 만들어야 한다 |
| 적외선 물체 감지 센서 (키트) | 디지털 출력이라 변환 칩 없이 GPIO에 연결한다. 키트마다 하나씩, 모두 2개 있다. 어두운 색 물건이나 센서에서 벗어난 위치의 물건은 놓칠 수 있어 시험이 필요하다 |
| 초음파 거리 센서 (키트) | 거리가 짧아진 것으로 물건을 안다. 흔히 쓰는 HC-SR04는 ECHO 핀이 5V를 내보내서 저항으로 전압을 낮춰 연결해야 한다([gpiozero 문서](https://gpiozero.readthedocs.io/en/stable/api_input.html)) |

### 브로커

| 방법 | 판단 |
| --- | --- |
| EC2에 Mosquitto | 지금 쓰는 EC2에 함께 띄운다. 가볍고 따로 드는 비용이 없다. Tailscale 주소에서만 접속을 받고, 장치마다 비밀번호와 주제 권한(ACL)을 준다([mosquitto.conf 설명서](https://mosquitto.org/man/mosquitto-conf-5.html)) |
| AWS IoT Core | 관리형 서비스라 운영 부담이 적고 강의자료에도 나온다. 기기마다 인증서와 정책을 만들어야 해서 준비가 더 걸린다 |

## 제안

- 촬영과 개방 같은 명령은 지금처럼 HTTP로 둔다. 결과(사진, 성공·실패)를 바로 받아야 하고, 백엔드와 연동 시험을 마친 흐름이다. 명령까지 MQTT로 옮기면 요청과 응답을 따로 짝지어야 한다.
- 물건 유무, 장치 연결 상태, 문 열림·닫힘처럼 장치에서 생기는 변화는 MQTT로 알린다.
- 브로커는 EC2의 Mosquitto로 시작한다.
- 센서 값만으로 보관·수령을 완료하지 않는다. 완료는 지금처럼 사용자의 완료 확인과 문 닫힘 조회로 정한다([D03·D06](../../../backend/docs/spec-review.md)). MQTT로 받은 상태는 경고와 화면 표시에만 쓴다.

주제 초안이다. 협의하면서 바꿀 수 있다.

| 주제 | 보내는 Pi | 값 |
| --- | --- | --- |
| `slf/<키오스크 ID>/capture/status`, `slf/<키오스크 ID>/locker/status` | 촬영 Pi, 보관함 Pi | `online`, `offline`(유언 메시지) |
| `slf/<키오스크 ID>/lockers/<칸 번호>/item` | 보관함 Pi | `present`, `empty` |
| `slf/<키오스크 ID>/lockers/<칸 번호>/door` | 보관함 Pi | `open`, `closed` |
| `slf/<키오스크 ID>/capture/item` | 촬영 Pi | `present`, `empty` |

모든 메시지는 QoS 1, 보존 메시지로 보내서 나중에 구독한 쪽도 현재 상태를 바로 받게 한다. 내용은 값과 측정 시각을 담은 JSON이다(예: `{"value": "present", "at": "2026-11-15T21:00:00+09:00"}`).

## 계획

1. Pi: 컨트롤러에 센서 읽기와 MQTT 발행을 더한다. 브로커 주소를 설정하지 않으면 MQTT를 쓰지 않고, 가짜 하드웨어 모드에서는 가짜 센서 값을 보낸다. 맥에 브로커를 띄워 먼저 시험한다.
2. 센서 시험: 키트의 적외선 물체 감지 센서를 보관함 칸에 달고, 물건의 크기·색·위치에 따라 잘 잡히는지 시험해 실험 기록으로 남긴다.
3. 연결: 팀과 정한 뒤 EC2 브로커에 두 Pi를 연결하고 백엔드·화면과 맞춰 본다.
4. 시연: Pi 전원을 뽑으면 화면에 꺼짐이 뜨고, 보관 중인 칸에서 물건을 꺼내면 경고가 뜨는 것을 보여 준다.

## 정할 것

- 브로커 설치·운영과 백엔드의 구독·경고 처리 (백엔드 담당)
- 상태를 보여 줄 화면 (프론트엔드 담당)
- 센서 배치: 적외선 센서 2개는 보관함 두 칸에 먼저 쓴다. 촬영 상자에 초음파 센서를 달지는 칸 시험 결과를 보고 정한다
