# 실험 0002. 실제 Pi로 MQTT 경고 종단 시험

- 날짜: 2026-11-21
- 장비: 촬영 Pi와 보관함 Pi(Raspberry Pi 4), 보관함 칸별 LED·버튼, EC2의 MQTT 브로커(Mosquitto, Tailscale 안), 운영 백엔드와 키오스크 웹
- 키오스크: `00000000-0000-0000-0000-000000000001`(Swagger 테스트 키오스크)
- 가상 센서 조작: [tools/sim.py](../../tools/sim.py)

## 왜 했나

가상 센서와 MQTT 발행(#40)은 맥에서 로컬 브로커로만 확인했다. 백엔드가 EC2에 브로커와 구독을 붙였으므로(#50, #51), 실제 두 Pi가 보낸 상태와 경고가 서버까지 저장되는지, 그리고 등록·보관·수령 흐름 안에서 경고가 맞는 때에 생기는지 확인했다.

## 방법

- 두 Pi에 최신 코드와 paho-mqtt를 설치하고, `.env`에 브로커 주소(EC2의 Tailscale 주소)·Pi별 계정·`PI_SIMULATION=true`·상태 파일 경로를 넣은 뒤 서비스를 다시 켰다([설치와 접속](../../deploy/setup.md)).
- 서버의 장치 상태 API(`/api/kiosks/{kiosk_id}/device-status`)에서 두 Pi가 online인지, 경고 API(`/api/alerts`)에서 경고가 저장됐는지 확인했다.
- 2차 시험은 백엔드 담당과 통화하며 진행했다. 키오스크에서 실제로 등록·보관·수령을 하고, 그 사이에 `sim.py`로 가상 무게를 넣고 뺐다. 서버 쪽 DB와 다시 열기 호출은 백엔드 담당이 맡았다.

## 1차 시험: 백엔드 명령 없이

| 시각 | 한 일 | 결과 |
| --- | --- | --- |
| 21:24 | 2번 칸 강제 개방(`locker 2 force-open`) | FORCED_OPEN(경보) 저장 |
| 21:24 | 1번 칸 강한 충격(`locker 1 shock strong`) | TAMPER(경고) 저장 |
| 21:25 | 2번 칸 버튼으로 닫기 | 물건이 없는 칸이라 추가 경고 없음(정상) |

Pi 서비스 로그에 `MQTT 연결됨`이 보이지 않았다. uvicorn이 자기 로거만 설정해서 Pi 로거의 INFO가 버려졌기 때문이라, 앱이 시작될 때 Pi 로거에 출력을 달도록 고쳤다(#52).

## 2차 시험: 등록·보관·수령 흐름

백엔드가 실제 Pi로 촬영(2장)과 개방 명령을 보내는 것을 Pi 로그로 확인했다.

### 1회차에서 찾은 문제

| 시각 | 상황 | 결과 |
| --- | --- | --- |
| 22:35:01 | 보관할 칸에 넣지 않고 닫음 | ITEM_NOT_DEPOSITED 저장 |
| 22:35:03 | 키오스크 '완료' | 보관 완료로 처리됨 |
| 22:39:27 | 수령할 칸에서 꺼내지 않고 닫음 | ITEM_NOT_TAKEN 저장 |
| 22:39:30 | '수령 완료' | 수령 완료로 처리되고 칸이 해제됨 |

경고는 맞게 왔지만, 백엔드의 보관·수령 완료가 문 닫힘만 보고 칸 상태(물건 있음·없음)를 보지 않았다. 원인과 고칠 방법을 정리해 백엔드 담당에게 전달했고, 백엔드가 칸 상태와 어긋나는 완료를 막고 다시 열기 API를 추가했다(#53).

### 2회차(#53 반영 뒤)

| 단계 | 시각 | 한 일 | 결과 |
| --- | --- | --- | --- |
| 보관 | 23:12:36 | 1번 칸에 넣지 않고 닫음 | ITEM_NOT_DEPOSITED, '완료'는 409 `ITEM_NOT_DETECTED`로 거절 |
| | 23:17:29 | 다시 열기(`deposit/reopen`) 뒤 넣고 닫음 | 23:17:54 보관 완료, 새 경고 없음 |
| 수령 | 23:22:54 | OTP로 연 칸에서 꺼내지 않고 닫음 | ITEM_NOT_TAKEN, '수령 완료'는 `ITEM_STILL_INSIDE`로 거절 |
| | 23:23:50 | 다시 열기(`pickup/reopen`) 뒤 꺼내고 닫음 | 23:24:14 수령 완료, 새 경고 없음 |
| 촬영 상자 | 23:27:27 | 사진 2(23:25:27) 뒤 촬영 상자에 물건을 남김 | 정확히 120초 뒤 CAPTURE_ITEM_LEFT |
| 도난 | 23:28:57 | 2번 칸 강제 개방 뒤 물건을 빼고 닫음 | FORCED_OPEN, ITEM_MISSING |

도난 시험 뒤에도 2번 칸의 물건이 DB에 stored로 남았다. 2번 칸에는 이 시험 전부터 보관 중인 물건이 있었고, 경고는 업무 상태를 바꾸지 않았기 때문이다. 가상 무게를 DB와 맞춘 뒤 백엔드에 전달했고, 백엔드가 ITEM_MISSING을 받으면 그 칸의 보관 물건을 missing으로 표시하고 칸을 비우도록 고쳤다(#54). 반영 뒤 다시 시험하자(23:55) FORCED_OPEN, ITEM_MISSING(23:55:59)에 이어 그 물건의 보관함 배정이 끝났다.

## 결론

- 경고 6가지(FORCED_OPEN, TAMPER, ITEM_NOT_DEPOSITED, ITEM_NOT_TAKEN, CAPTURE_ITEM_LEFT, ITEM_MISSING)가 실제 Pi에서 서버까지 저장된다.
- 보관·수령 완료는 칸 상태와 어긋나면 거절되고, 다시 열기로 마칠 수 있다.
- 강제로 가져가면 DB에도 반영되어 그 물건은 수령·검색 대상에서 빠진다.

## 시연 때 주의할 점

- 가상 무게를 넣거나 뺀 다음에 버튼을 누른다. 명령이 Pi에 닿는 데 2~3초 걸려서, 버튼을 먼저 누르면 1회차처럼 '보관 안 됨'이 된다.
- 시연 전에 DB에서 보관 중인 칸과 가상 무게를 맞춘다(`sim.py locker N preset 150`, 빈 칸은 `sim.py locker N clear`). 이번에 2번 칸이 어긋나 있었다.
- 프론트를 배포한 뒤에는 키오스크 페이지를 새로고침한다. 배포 전에 연 페이지는 새 안내 문구 대신 일반 오류 문구를 보였다.
- 키오스크에 다시 열기 버튼이 아직 없어 이번에는 Swagger로 호출했다(프론트 담당에게 요청).
